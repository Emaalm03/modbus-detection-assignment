# Attack 5B: High-Volume Modbus/TCP Connection (Rule 100016)

This alert is related to a single TCP connection containing a very high number of packets from a non-authorized source to the PLC.

## Step 1: Validate the alert

The analyst should check the rule ID, alert level, source and destination addresses, connection duration, and packet counts. In this case, Rule `100016` generated a level-`13` alert. The connection lasted approximately `15.01` seconds and contained `22,669` origin packets and `22,664` response packets. This indicates a high-volume connection that exceeds the configured threshold of 1,000 origin packets.

## Step 2: Identify the source

The analyst should check `data.conn_id.orig_h` and `data.conn_id.resp_h` to identify the source and destination. In this case, the source is `192.168.56.6` (attacker VM), and the destination is `192.168.56.4` (PLC), using TCP port `502`. The authorized master is `192.168.56.3`. Since the connection comes from a source that is not the authorized master and contains a very high number of packets, the activity requires further investigation.

## Step 3: Examine the Modbus requests

The analyst should examine the corresponding PCAP and `modbus.log` to understand the traffic exchanged during the connection. In this scenario, repeated `READ_HOLDING_REGISTERS` requests and responses were observed. The analyst should review the function codes, request and response sequence, and timing to determine whether the traffic differs from normal communication.

The high-volume rule is based on connection metadata rather than a specific Modbus function. Therefore, the same rule can identify a high-volume connection even if another Modbus function is used.

## Step 4: Compare with the baseline

The analyst should compare the observed packet count and connection duration with normal traffic generated by the authorized master. This helps determine whether the connection volume is unusual for the simulated environment. The analyst should also verify whether the source was expected to communicate with the PLC during the capture.

## Step 5: Check the process impact

The analyst should check whether the PLC or simulated process shows unexpected changes, such as abnormal tank-level behaviour, delayed responses, or a loss of communication. These observations can help determine whether the traffic affected the simulated process. A high packet count alone does not prove that the PLC was disrupted or that the physical process was affected.

## Conclusion

The activity is suspicious because a single connection from the attacker VM to the PLC contains `22,669` origin packets within approximately 15 seconds. Rule 100016 identifies this high-volume connection because it exceeds the configured packet threshold and matches the non-master connection rule. The analyst should examine the Modbus requests, compare the traffic with the baseline, and check for process impact before deciding whether the activity caused any disruption.
